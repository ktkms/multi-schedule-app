## 位置づけと判断の優先順位

日付先行型は、飲み会・会食・旅行など、まず集まれる日を決めたい用途に対応する。既存の日時先行型を維持し、同じイベント・公開URL・参加者のまま詳細時間調整と日時確定まで進める。

- 本書の「確定仕様」は[Issue #257](https://github.com/ktkms/multi-schedule-app/issues/257)の後続決定と、2026-11-02の設計レビューで再確認したサービス方針を整理したもの。
- 過去案と後続の確定事項が違う場合は、後続決定を優先する。Issueの古い未決チェック項目を、後続で解消した論点の再質問理由にしない。
- 「設計提案」「未確定」は確定仕様ではない。DB・RPCの詳細は[技術設計](../docs/architecture/date-first-scheduling.md)を参照する。
- 参照チャットで言及された添付ZIP・SQLドラフトの本文は未取得。そこにだけある仕様は推測で採用しない。
- 文書化は実装完了・本番適用を意味しない。既存の日時先行型の挙動を本書によって変更しない。

## 確定仕様

### 利用と編集

- 通常のWeb操作はログイン不要。作成、回答、回答編集、集計、候補追加、詳細時間調整、日付・日時の確定と解除を含む。
- 共有イベントURLを知る利用者は、イベント内の既存参加者を明示選択して回答を編集できる。他参加者の回答の共同編集を許容する。
- participant IDは編集対象を示す。本人認証の証明ではない。同名の参加者を名前だけで自動統合しない。新規登録と既存参加者編集を区別する。
- 主催者専用権限、秘密編集リンク、編集コード、必須ログインを追加しない。別端末・Cookie消去後も共有URLから編集できる。
- 参加者一覧、回答、日付別コメントは共有URLの閲覧者全員に公開する。コメントごとの公開設定は設けない。
- ログインはアカウント予定・履歴などの利便性を追加する。アカウントへの書き込みでは認証済みの本人と対象の紐付けを検証する。
- MCPなど自動操作はOAuthと本人の紐付けを必要とする。Webの共同編集権限をそのまま拡張しない。
- 公開URLでの共同編集とDB匿名ロールの直接アクセス権限は別の問題。[アクセス方針](../docs/architecture/access-policy.md)に従ってサーバー経由で処理する。

### 初回実装の範囲

1. 日付先行型のイベントを作成し、候補日を共有する。
2. 日付ごとの○・△・×・未回答を入力・編集する。
3. 日付別集計、△の時間条件、コメントを比較する。
4. 必要なら候補日を追加する。
5. 日付のみで確定する、または同じイベントで詳細時間調整へ進む。
6. 対象日・時間候補を設定し、詳細時間回答を収集する。
7. 日時を確定・変更・解除する。

日付だけで十分なら、詳細時間調整へ進まずに完了できる。工程を分割して開発しても、初回公開の範囲を日付回答だけに縮小しない。

### 作成と候補日追加

- 「日付から決める」と「最初から時間も決める」を区別する。既存の自動・手動は日時候補の入力方法として維持する。
- 日付候補は時刻を持たない暦日。作成後も追加できる。
- 追加日は登録済み参加者に対して未回答から始まる。既存の回答・コメント・△時間・詳細時間回答・確定結果を変更しない。
- 登録済み参加者が追加候補に未回答の状態と、参加者として未登録の状態を区別する。追加通知や高度な旅行日程モデルは今回の確定範囲に含めない。
- 作成時の朝・昼・夜・全日などの時間帯設定は任意・複数選択可能とする。必要なら詳細設定を使う。厳密な時刻境界と画面配置は後述の未確定事項。

### 日付回答と保存

| 回答   | 意味                                              | 保存するデータ                                                           |
| ------ | ------------------------------------------------- | ------------------------------------------------------------------------ |
| ○      | 当日0〜24時は基本的に参加可能。翌0〜6時は含めない | ○と任意の日付別コメント                                                  |
| △      | 条件次第で参加可能                                | △、任意の参加可能時間区間、任意の日付別コメント                          |
| ×      | その日は参加不可                                  | ×と任意の日付別コメント                                                  |
| 未回答 | 可否をまだ回答していない                          | 回答値・時間区間・コメントなし。手動で戻した事実は自動反映の保護用に記録 |

- 全候補×でも保存できる。全候補未回答の明示保存も受理し、参加者の登録は残す。○が1件以上あることを送信条件にしない。
- 同じ記号を単独再タップすると、その日を未回答へ戻す。回答解除専用アイコンは設けない。
- ドラッグは開始記号を塗る。選択済み記号から始めても解除せず、同じ日を何度通っても反転しない。
- ドラッグ中はレイアウトを固定し、終了後に新たに△になった日付の時間UIをまとめて開く。既存の△を自動で閉じない。
- 変更した日だけを保存する。入力に含めない別日付や別参加者の回答を上書きしない。
- 共同編集が競合した場合、古い画面の入力で黙って上書きしない。最新状態を確認して再編集できるようにし、未送信入力を無警告で破棄しない。

### △時間・コメントの保持

| 操作                  | 同じ編集画面内                                              | 保存後                                                                  |
| --------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| △から○・×へ変更       | 元の△時間を一時保持。△へ戻すと復元                          | △時間を削除                                                             |
| ○・△・×間で変更       | コメントを保持                                              | コメントを保持                                                          |
| 未回答へ変更          | コメントと△時間を一時保持。保存前に対応する回答へ戻せば復元 | 当日の回答値・コメント・△時間を消去。手動未回答の保護用メタデータは保持 |
| △の時間を未指定にする | 全マス未選択を表示                                          | 時間区間なしの△として保存                                               |

- 未回答中はコメントを編集できない。コメント入力済みはアイコン自体の小さなサインで示し、追加ラベルやバッジを付けない。
- 上記の一時保持は同じ編集画面内だけ。開閉状態と一時保持用データをDB・Web Storageへ永続化しない。旧ウィザードの下書き復元を無条件に適用しない。
- △の時間なしは不可や終日可へ変換しない。「時間未指定」のラベルや常時の要約文は追加しない。

### 時間グリッドと結果表示

- △の時間入力は基本1時間単位で、すべての画面幅で1行12時間を維持する。専用の横スクロールは設けない。
- △の時間入力には「可能な時間を入力してください。」を表示する。
- 表示範囲の先頭の時間セルの前と、末尾の時間セルの後に＋を1個ずつ置き、早い方向・遅い方向へ1回1時間ずつ表示範囲を延長する。＋は時間セルと同じ行に置き、折り返しの途中には重複させない。追加マスは未選択で、時刻順に並べて12時間ごとに折り返す。
- 表示範囲を広げただけではDBへ保存せず、選択した時間区間だけを保存する。不連続な区間を間の時間まで結合しない。
- 結果画面は日付ごとの○・△・×・未回答人数を一覧表示し、日付行の直下に参加者詳細を展開する。人数の意味を混ぜず、○＋△を確実な時間別参加人数として使わない。
- 日付詳細とコメントは複数同時に開ける。初期状態はすべて閉じる。別の日付を開いても既に開いた日付を閉じない。
- 日付詳細を閉じると、その日付内のコメント開閉状態だけをリセットする。コメント本文と別日付の開閉状態は維持する。
- コメント本文は入力済みアイコンから開く。常時本文・短文プレビューは表示しない。
- 参加者は○→△→×→未回答の順。同状態内は参加者登録順（created_at昇順、同値はid昇順）。
- △の時間条件は本人の氏名の近くに全件表示し、自然に折り返す。氏名直下を第一候補とし、配置は実画面で比較する。

### 日跨ぎと○の意味（2026-11-02追加決定）

- 候補日の当日0時から翌日6時終了までを、その候補日の△時間・詳細時間候補として扱える。前日への拡張、翌6時を超える拡張は初回には含めない。
- 日付○は当日0〜24時が基本的に参加可能という申告。翌0〜6時まで参加可能とは推定しない。以前の「○は終日可ではない」という定義は、この追加決定で置き換える。
- 終了が翌日ちょうど0時なら24:00と表記する。それ以降は「翌1:00」など日付の違いを明示し、25時等だけの表記に依存しない。月末・年末も実際の翌日へ進める。
- 日付○であっても詳細時間の正式回答は自動生成しない。アカウントの実際の予定に基づく時間補完は、後述の別経路として扱う。

### 詳細時間調整

- 日付回答、日付別コメント、△時間はそのまま残す。詳細時間回答の変更で日付回答を黙って書き換えない。
- ○・時間なし△・×・未回答から詳細時間の正式回答を自動生成しない。×の日付はその状態を区別表示し、詳細時間の再回答は可能にする。
- △の選択時間は参照・編集可能な初期案。明示確認・保存まで正式回答へ変換せず、保存済みの詳細回答を再移行で上書きしない。
- 詳細時間も○・×・未回答を区別する。時間枠を省略した更新は、その枠を×や未回答にしない。
- 日付確定があれば時間調整対象は確定日集合に限定する。確定前にも複数の候補日を明示選択して時間調整できる。
- 対象外になった日の時間候補と詳細回答は保持し、現在の時間集計・確定・同期から除外する。同じ候補へ戻した場合だけ回答を復帰させる。
- 変更された時刻へ、以前の候補の回答を自動転用しない。

### 確定と解除

日付のみ確定、日時付き確定、複数日の混在確定を扱う。調整中であることと確定結果の有無は別に表示する。

| 操作                       | 日付確定                 | 日時確定                     | 保存済み回答             |
| -------------------------- | ------------------------ | ---------------------------- | ------------------------ |
| 日付のみ確定               | 選択日を確定             | 自動作成しない               | 保持                     |
| 確定済み日付の時間調整開始 | 維持                     | 維持                         | 保持                     |
| 日時確定                   | 対応する日付の確定が必要 | 選択枠を確定                 | 保持                     |
| 日時だけ解除               | 維持                     | 対象枠を解除                 | 保持                     |
| 日付を確定集合から外す     | 対象日を解除             | 影響枠を明示確認後、同時解除 | 保持・対象外として休止   |
| 日付を再確定               | 対象日を確定             | 過去の確定を自動復活させない | 同じ時間候補の回答を復帰 |

日付を外す確認は最新状態で再検証する。確認後に他の利用者が確定内容を変えていた場合は、無変更で再確認へ戻す。日付と関連日時の解除を部分成功させない。

### △から詳細時間への提案

- 選択済み△区間の和集合が候補枠全体を覆う場合だけ、その枠を○の初期案として扱う。
- 例えば18〜20時の申告なら18〜19時・19〜20時は○の初期案。18:30〜19:30の申告から18〜19時を○に拡大しない。重なる実区間だけを参照表示する。
- 提案がない枠は未回答。申告外という理由で×の提案を作らない。
- 保存済みの○・×・明示的な未回答は初期案で上書きしない。未保存の提案と正式回答を表示・保存処理で区別し、採用内容を確認して保存したものだけを正式回答にする。

### カレンダー出力の契約

- 確定日ごとに、日時確定があればその日時だけ、なければ時刻未定の日付予定を出力する。日付のみと日時付きの予定を同じ親候補日について重ねない。
- 時刻未定のICSはDTSTART/DTENDにDATE値を使い、終了は翌日の排他的境界、TRANSPはTRANSPARENTとする。タイトルには「時間未定」を付ける。仮の基本時間を出力しない。
- 日付のみ予定と日時付き予定には異なる安定UIDを使う。複数日時を1件のUIDへまとめない。解除・再確定しても同じ候補のUIDは変えない。
- Google追加リンクも時刻未定を日付予定として扱う。リンクだけで外部カレンダーの空き時間扱いを制御できるとは保証しない。生成パラメータと実表示は実装時に確認し、不明なパラメータを確定仕様として実装しない。
- 静的ICSの取り込み済みコピーやGoogle追加リンクは、アプリで変更・解除しても自動更新・削除できるとは説明しない。日付のみから日時付きへ変えた後の再出力は現在の確定内容だけを返す。
- 時刻未定はDaySynth内の予定競合を作らず、現在有効な確定日時だけが競合参照の対象になる。

### アカウント予定からの自動判定と手動保護

MCP操作・アカウント予定からの自動反映も初回実装に含める。前回の「新方式では後続対応とする」案は採用しない。日付記号も自動判定するが、基本時間帯だけを見て終日可と推定せず、当日0〜24時の既知の予定を基準にする。

| 当日0〜24時の予定                                                        | 日付の提案・反映値          |
| ------------------------------------------------------------------------ | --------------------------- |
| 全時間が参加可能として被覆され、不可・他イベントの確定日時との重複がない | ○                           |
| 一部に参加可能な区間があり、残りに不可または不明がある                   | △と、判定できた参加可能区間 |
| 全時間が不可として被覆される                                             | ×                           |
| 参加可能と判断できる区間がなく、不明な時間が残る                         | 未回答                      |

- 未登録の予定は不明。不可との重複区間は可より優先し、同じイベントの確定日時を自己競合として扱わない。
- 翌0〜6時は当日の記号判定に使わない。判定が△の場合は、翌朝までに判明した参加可能区間も△時間へ補完する。翌朝の詳細時間候補にも翌日の実際の予定を参照する。
- 詳細時間は、不可との重複があれば×、枠全体を可が覆えば○、どちらでもなければ未回答。日付記号を時間回答へコピーする処理とは分離する。
- 新規回答画面で予定を読み取っただけでは保存しない。回答送信・MCPの明示保存・既存の予定反映操作が正式保存の境界。
- 手動で記号・時間を変更した対象は自動反映から保護する。手動で未回答へ戻した対象も勝手に埋め直さない。コメントだけの編集は判定値の自動反映設定を変えない。
- 再反映はアカウント由来の回答または未編集の対象に限定し、手動保護の解除は対象と差分を示した明示操作にする。○・×・未回答、過去候補、休止回答を全件置換しない。
- 自動判定が不明へ変わった場合は、アカウント由来の古い判定を未回答へ戻す。コメント付きの日付が未回答になる場合は、削除対象を確認してから適用する。未確認なら当該イベントの反映は全件無変更で止め、再確認が必要な結果を返す。
- 日付回答・詳細時間回答とアカウント予定は別データ。日付○・×や時刻未定の確定だけから、終日の予定ブロックをアカウントへ自動保存しない。
- 詳細時間の正式回答をアカウントへ保存する場合は本人の明示操作とプレビューを必要とし、未回答を×として書き出さない。曖昧な端数を1時間の可に拡大しない。

自動反映でも、未回答として保存する日付にはコメントを残さない。コメント削除の影響がある反映は確認を挟むため、無確認の削除や隠し保存は発生させない。

### MCPの対応範囲

- 初回から、イベント検索・取得、本人の日付/詳細回答の取得・保存、予定の参照・変更・反映、詳細回答のアカウント保存に対応する。
- 既存のツールを方式と回答段階で拡張し、新方式の回答を旧boolean契約へ押し込まない。旧方式の入力・出力は維持する。
- 保存対象の参加者はOAuth本人の紐付けから解決する。任意のparticipant ID・user IDを入力させない。初回回答は本人用参加者と紐付けを一括作成する。詳細時間段階から初めて参加する場合も同じイベント内で新規回答できる。
- 対象は既存8ツールの新方式対応。現行MCPにはイベント作成・候補設定・確定のツールがないため、そのような新規ツールの追加とは分ける。Webでは初回から作成〜日時確定まで提供する。
- 別イベントへの越境、休止候補への更新、古いrevisionでの無言上書き、保護された手動未回答の自動補完を拒否する。

### 直接日時を確定する場合

D（確定日集合）が空の状態から日時を確定するときは、UIが既存Dと選択日時の親候補日との和集合を希望Dとして組み立てる。新しく確定する日付・日時を同じ確認画面に提示し、希望D/Fの両方を保存する。サーバー側で親日付を勝手に補完したり、確認していない日付を確定したりしない。

### UI数値の初期案と残る確認

以下は実装比較用の初期案であり、ユーザー決定とは区別する。

- 基本表示は10〜22時、朝6〜12時・昼12〜18時・夜18〜24時・全日0〜24時。全日は他のプリセットを包含する扱いとする。
- プリセットは表示/補完の基本範囲であり、日付○の判定範囲や可否を変えない。朝＋夜など不連続な選択でもグリッドは時刻順に連続表示し、空白時間を参加可能として選択しない。
- プリセットと詳細設定は同じ区間集合を編集する。プリセット選択は対応区間の和集合へ置換し、詳細編集後は一致するプリセットだけを選択状態へ戻す。
- 氏名100文字、日付別コメント2000文字を、既存MCPの上限を踏まえた初期案とする。日数・総候補数・要求サイズの設計値は後述の入力上限へ整理する。頻度制限は技術設計の運用初期案を参照する。
- ＋配置、折り返し幅、ドラッグ判定、コメントのサインは実画面で検証する。これらの比較のために主要な確定UXを再質問しない。

### 入力上限の設計値（2026-11-03）

次は初回実装の設計値であり、既存日時先行型へ遡及適用しない。実装前の隔離DB・要求サイズ検証で調整する場合は、根拠と影響を本書へ記録する。負荷確認済みの保証値とはしない。

| 対象                  | 設計値                                    | 扱い                                                                                 |
| --------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------ |
| イベントタイトル      | 1〜200文字                                | 前後の空白を除去。空白だけは不可                                                     |
| 説明                  | 0〜5000文字                               | 省略可                                                                               |
| 参加者名              | 1〜100文字                                | 前後の空白を除去。同名は許す                                                         |
| 日付別コメント        | 0〜2000文字                               | 空文字はコメントなしへ正規化                                                         |
| 日付候補              | 1イベント90日まで                         | 飛び飛び日付を許す。最初と最後の間隔ではなく候補日数を数える                         |
| 詳細時間候補          | 有効3000枠、引退済みを含む総数12000枠まで | 回答を消して枠を空けない。同一IDの復活は総数を増やさない                             |
| △区間                 | 正規化後1日900区間まで                    | 0〜1800分の整数分区間で、隣接区間を結合した場合の理論上限。画面は基本1時間単位を維持 |
| 日付回答の1回の差分   | 90日まで                                  | コメント・区間を含めて原子的に保存                                                   |
| 時間回答の1回の差分   | Webは3000枠、MCP回答は1000枠まで          | MCPの既存制限を維持。超過は全件拒否し、明示的に対象を絞る                            |
| 候補設定の1回の差分   | 新規/復活は合計3000枠、引退は3000枠まで   | 全入れ替えも同一処理で検証。更新後の有効枠・総枠上限を別に確認                       |
| 新方式Webの正規化JSON | UTF-8で768KiBまで                         | フレームワークの本文制限とは別に検証する                                             |
| MCPのHTTP本文         | 128KiBまで                                | JSON-RPCの外側を含む現行制限を維持                                                   |

文字数は新方式ではUnicodeコードポイント数で数え、DBのchar_lengthと一致させる。旧MCPの文字数判定はこの文書だけで変更しない。文字数・件数を満たしていても本文サイズ超過なら保存できないため、画面でも送信前に確認し、入力は保持して超過対象を案内する。

900区間は頻繁な分断を実装上推奨する値ではない。1分ごとの交互選択でも区間を丸めたり、間を可として結合したりしないための数学的な上限で、実際の保存は本文サイズの制約も受ける。

読み取りは1000行等のページ境界で切り捨てず、全ページ取得または明示的なページ情報を返す。書き込みの自動分割・部分成功によって、この上限を回避しない。人数の上限は今回新設せず、集計とページ取得の負荷を別途測定する。

### 保存結果と競合時の利用者への応答

- 通常保存は成功または全件無変更の失敗。候補追加・確定変更・回答保存を部分成功として扱わない。
- 古い回答revision、無効な対象、確認内容の変化、入力上限を区別する。再入力を求める前に現在値と未送信入力を比較できるようにする。
- DBで確定済みの保存後に予定反映・画面再検証が失敗した場合は、「回答の保存は成功、後処理は未完了」と区別する。同じ回答を新規作成として再送しない。
- 頻度制限はログインを必須にする仕組みとして使わない。匿名Webでは共有回線の複数参加者を想定し、参加者全員を一つの本人として制限しない。
