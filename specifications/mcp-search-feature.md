# MCP検索・予定取得の追加仕様案

## 1. 目的と状態

状態: 未実装の仕様案。本書は今後の追加仕様を定める。現在の実装範囲については[既存のMCP設計](../docs/architecture/mcp.md)を参照する。

MCPクライアントから、本人に紐づくイベントを期間・名前・確定状態で検索できるようにする。既存の読み取りツールを拡張し、回答・予定の保存処理は変更しない。

イベント検索、確定日時の取得、任意期間の本人予定取得を同じ実装範囲に含める。内部の作業と検証はツールごとに分け、3機能の受け入れ条件を満たした時点で本仕様の実装を完了とする。

## 2. イベント検索: `list_my_events`

### 入力

| パラメータ     | 意味                                                                        | 省略時                  |
| -------------- | --------------------------------------------------------------------------- | ----------------------- |
| `date_from`    | 検索開始日。`YYYY-MM-DD`                                                    | 期間で絞らない          |
| `date_to`      | 検索終了日。`YYYY-MM-DD`。終了日も含む                                      | 期間で絞らない          |
| `date_target`  | `effective`: 状態に応じた日時、`candidate`: 候補日時、`finalized`: 確定日時 | 期間指定時は`effective` |
| `query`        | イベント名の部分一致検索。前後の空白を除去し、1〜100文字                    | 名前で絞らない          |
| `is_finalized` | `true`: 確定済み、`false`: 未確定                                           | 状態で絞らない          |
| `offset`       | 絞り込み後のイベント一覧の取得開始位置。既存の0〜100000を維持               | `0`                     |
| `limit`        | 1回に取得するイベント数。1〜100                                             | `100`                   |

- `date_from`と`date_to`は両方指定するか、両方省略する。片方だけの指定はエラーとする。
- 実在する日付であることを検証し、`date_from <= date_to`を必須とする。同じ日付は1日分の検索となる。
- `date_target`は期間指定時だけ指定可能とする。
- 複数の条件はANDで適用する。`query`の英字は大文字・小文字を区別せず、`%`や`_`は検索演算子ではなく文字として扱う。空文字はエラーとする。
- `date_target: finalized`と`is_finalized: false`の併用は矛盾するためエラーとする。

### 期間の判定

日付は日本時間として扱い、開始日の0時以降、終了日の翌日0時より前の期間に変換する。日時枠が検索期間と重なる条件は次のとおりとする。

```text
日時枠のstart_time < 検索期間の終了
AND 日時枠のend_time > 検索期間の開始
```

- 対象の日時枠が1件でも重なればイベントを返す。枠全体が期間内に収まる必要はない。
- 日をまたぐ枠も対象とし、検索開始時刻に終了する枠、検索終了時刻に開始する枠は除外する。
- `candidate`では確定状態にかかわらず候補日時を検索する。
- `finalized`では確定済みイベントの確定した日時だけを検索する。採用されなかった候補日時は対象にしない。
- 既定の`effective`では、未確定イベントは候補日時、確定済みイベントは確定日時を検索する。「来週のイベント」など、検索対象の指定がない依頼に使う。
- 「候補があるイベント」は`candidate`、「開催が確定したイベント」は`finalized`を指定する。`candidate`と`is_finalized: true`の組み合わせも有効とし、確定済みイベントの元の候補を調べる用途に使える。

### 結果とページ分割

- 検索対象は従来どおり本人のアカウントに紐づくイベントに限定する。
- `events`の既存の`title`、`public_token`、`is_finalized`と、トップレベルの`next_offset`を維持する。
- 期間指定時はトップレベルに`date_target`と`time_zone: Asia/Tokyo`を返す。イベントごとに`matched_date_target`（`candidate`または`finalized`）と`matched_dates`を追加し、状態に応じて実際に検索した対象を明示する。各枠は`id`、`start_time`、`end_time`を返す。期間指定がなければこれらの追加フィールドを返さない。
- 一致した枠は開始日時、終了日時、IDの順に昇順で返す。表示用に枠の開始・終了を切り詰めず、元の日時を返す。
- 応答量を抑えるため、`matched_dates`はイベントごとに先頭3件までとし、残りがある場合は`matched_dates_truncated: true`を返す。残りがなければ`false`とする。期間指定時だけこのフラグを返す。全日時が必要な場合は`get_event`を使い、同じ期間条件で絞る。MCPクライアントは、切り詰められた一覧のみで期間内の対象日時が網羅されていると判断してはならない。
- 条件の適用とイベントの重複除去を行ってから、`limit`件単位でページ分割する。候補枠が複数一致してもイベントは1件と数える。MCPクライアントが少数の結果を必要とする場合は`limit: 20`などを指定できる。
- 期間指定時は最初に一致した枠の開始日時、本人イベント紐づきIDの順に昇順で並べる。枠の開始が検索開始より前でも元の開始日時で並べる。期間を指定しない場合は既存の本人イベント紐づきIDの昇順を維持する。
- 絞り込み後に続きがあることを確認できた場合だけ、`next_offset: offset + limit`を返し、続きがなければ`null`を返す。内部では`limit + 1`件を確認する。既存の「末尾がちょうど100件の場合に空の次ページを案内する」挙動は改善する。
- 次ページには同じ検索条件を渡す。ページ間の追加・削除に対する一覧のスナップショットは保証しない。
- 取得失敗を0件として返さない。
- 既存の100件を取得してからそのページだけを絞る実装は不可とする。条件に合うイベントが後続にあっても検索から漏れないよう、サーバー側で検索条件と並び順を適用してからページ分割する。本人の全イベントと全候補を毎回取得する方式も採用しない。

### 利用例

「10月10日〜20日に候補がある未確定イベント」は次の入力とする。内部の検索終了は10月21日0時になる。

```json
{
  "date_from": "2026-10-10",
  "date_to": "2026-10-20",
  "date_target": "candidate",
  "is_finalized": false
}
```

「11月に開催が確定している、名前に『打合せ』を含むイベント」は次の入力とする。

```json
{
  "date_from": "2026-11-01",
  "date_to": "2026-11-30",
  "date_target": "finalized",
  "query": "打合せ"
}
```

## 3. 任意期間の予定取得: `get_my_schedule`

- 既存の`week_start`による指定日から7日間の取得を維持する。
- 新たに`date_from`・`date_to`を追加する。日付の形式、終了日の包含、重なりの判定はイベント検索と共通にする。
- `week_start`指定と、`date_from`・`date_to`の組による指定のいずれかを必須とする。両形式の併用と日付の片方だけの指定はエラーとする。
- 任意期間は終了日を含めて最大31日間とする。
- 任意の`availability`フィルタを追加する。`true`は登録済みの参加可能枠、`false`は登録済みの参加不可枠を取得し、省略時は両方を取得する。どちらの期間指定形式でも利用できる。
- 既存の`blocks`と`time_zone: Asia/Tokyo`を維持し、元の日時枠を返す。
- フィルタは保存済み予定ブロックの値を対象とする。確定イベントとの照合を含む最終的な参加可否判定を代替しない。
- 未登録の時間は返さず、参加可能とは推測しない。空の結果は「条件に一致する保存済み予定がない」ことを示す。

## 4. 確定日時の取得: `get_event`

- 既存の入力と候補日時の`dates`を維持する。
- `finalized_dates`を追加し、確定した候補枠の`id`、`start_time`、`end_time`を返す。`id`は`dates`と共通の候補日時IDとする。
- 未確定の場合は`finalized_dates: []`とする。確定済みでも確定枠が0件の場合は空配列を返し、候補全体を確定扱いしない。そのイベントは`effective`・`finalized`の期間検索では一致しない。DBへの問い合わせが失敗した場合は、0件と区別してエラーとして返す。
- 確定枠が複数ある場合はすべて返し、開始日時、終了日時、IDの順に昇順で並べる。
- 公開トークンによる既存の取得範囲は維持する。本人への紐づきを必須とするイベント検索とは区別する。

## 5. 互換性と権限

- 読み取り用の`daysynth.read`を維持する。新しいOAuth scopeや書き込みツールは追加しない。
- 本人の識別は認証情報から解決し、検索入力にユーザーIDを追加しない。
- 日時の出力は既存の日本時間の壁時計時刻表現を維持する。保存表現の`Z`や`+00:00`を理由に9時間加算しない。
- 不明な入力フィールドと不正な組み合わせを拒否し、既存のMCPエラー形式を維持する。
- フィルタ省略時のイベント一覧の項目・並び順・既定の取得件数を維持する。`next_offset`の末尾判定は上記のとおり改善する。既存の予定取得入力・出力を維持する。

## 6. 実装時の受け入れ条件

- 1日検索、終了日当日の枠、日をまたぐ枠、月末・年末・うるう日を正しく検索できる。
- 検索期間と境界が接するだけの枠を除外できる。
- 採用されなかった候補日時は、候補日時検索では対象となり、確定日時検索では除外される。
- `date_target`省略時は`effective`として、確定状態に応じた日時で検索される。確定済みで確定枠が0件の場合、不採用候補へフォールバックしない。
- 複数条件をANDで適用し、名前検索の特殊文字を文字として扱える。
- 複数候補が一致してもイベントが重複せず、フィルタ後の`limit`件単位の取得、開始日時による並び順、一致枠3件への切り詰めを検証できる。
- 一致イベント数が要求件数（`limit`）ちょうどで後続がない場合に`next_offset: null`となり、続きがある場合は同じ検索条件で次の結果を取得できる。
- 他人にだけ紐づくイベント・他人の予定が本人検索に含まれない。
- 不正な日付、逆転した期間、入力の矛盾、範囲外の`limit`を拒否する。任意期間の予定取得では32日以上の期間も拒否する。
- 未登録の時間を参加可能として返さず、データ取得エラーを空の正常結果にしない。
- 実際のMCP SDKクライアントから追加パラメータを指定でき、既存入力も継続して利用できる。

## 7. 今回の対象外

本人の回答によるイベント絞り込み、空き時間の自動提案、複数人の共通日程検索、履歴・お気に入りによる検索、イベント作成・編集・確定・削除は含めない。

実装時に本書と既存のMCP設計を同期し、利用者向け変更を`docs/CHANGELOG.md`へ追記する。仕様案の作成時点では実装済みの機能として変更履歴へ記載しない。
