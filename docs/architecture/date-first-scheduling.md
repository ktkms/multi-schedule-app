## 設計の前提

[機能仕様](../../specifications/date-first-scheduling.md)をサービス挙動の正本とする。確定済みUX、今回の技術設計案、未確定境界を区別し、過去のSQL・アーキテクチャ案をそのまま採用しない。

本書では、新方式の保存境界を分離し、既存の日時先行型を維持する追加中心の設計を推奨する。日跨ぎ対応のための時刻一意制約の切替は、既存行の同等な重複禁止を維持して行う。名称・列・制約の実装詳細は隔離DBでの検証後に確定する。

## 推奨する保存モデル

### 既存テーブルの拡張

| テーブル         | 追加案                                                                                                                  | 維持するもの                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| events           | scheduling_mode、adjustment_stage、revision、新規作成用creation_request_id/creation_payload_hash                        | 既存行はtime_first。旧方式の確定フローを維持                                    |
| participants     | day_answers_revision、detail_answers_revision、新規作成用creation_request_id/creation_payload_hash、UNIQUE(id,event_id) | 同じ参加者IDと登録順。全未回答でも行を残す                                      |
| event_dates      | candidate_day_id NULL可、retired_at NULL可、UNIQUE(id,event_id)。一意性は後述の方式別索引へ変更                         | start_time/end_timeの壁時計表現。旧行の追加列はNULL、旧方式の時刻重複禁止を維持 |
| finalized_dates  | 新方式でも既存の日時確定を利用。イベント所属の複合参照を検討                                                            | time_firstの確定データを移し替えない                                            |
| user_event_links | 新テーブルを作らず共用                                                                                                  | OAuth本人の回答との紐付け。共同編集で他人のアカウントへ自動的に紐付けない       |

scheduling_modeは作成時に決め、既存イベントの方式変換は行わない。新方式ではadjustment_stageをdays/times、旧方式ではNULLとすることを提案する。候補・回答が残っているだけでは現在の調整段階を判定できないため、段階は明示的に保持する。

### 新規4テーブル案

| テーブル                  | 主なデータ・制約                                                                                                                                                                                    |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| event_candidate_days      | id、event_id、local_date DATE、confirmed_at NULL可、prefinal_time_target。UNIQUE(event_id,local_date)、UNIQUE(id,event_id)                                                                          |
| event_day_responses       | id、event_id、participant_id、candidate_day_id、status yes/maybe/no/NULL、source manual/account、comment、updated_at。UNIQUE(participant_id,candidate_day_id)。参加者・候補日とevent_idを含む複合FK |

| date_first_time_responses | event_id、participant_id、event_date_id、availability boolean NULL可、source manual/account、updated_at。UNIQUE(participant_id,event_date_id)。参加者・日時候補とevent_idを含む複合FK               |

日付回答はyes/○・maybe/△・no/×、詳細回答はtrue/○・false/×。どちらも行なし、または手動保護用のNULL行は未回答として取得する。NULL行を回答済みとして数えない。△に時間区間0件も許す。確定日集合はconfirmed_at IS NOT NULLで取得する。

### 自動反映を初回に含めることによる設計変更

初回にMCP・自動反映を含めるという追加決定により、前回の「未回答は必ず行削除」という技術案を修正する。行を削除するだけでは、手動で未回答に戻した枠と未編集の枠を区別できず、次の同期で回答を埋め直してしまうためである。

- 新しい両回答テーブルにsourceを持たせる。手動操作はmanual、アカウント予定の判定を正式に保存する操作はaccount。コメント単独編集はsourceを変えない。
- 明示的に未回答へ戻す場合は、値NULL・source=manualの行を残す。日付コメント・△区間は消す。これは回答値の保持ではなく自動反映からの保護用メタデータであり、本人認証や履歴ではない。
- 未登録の未回答は行なし。account判定が不明になった場合は、元のaccount行を削除する。source=accountでNULLの行を保存しないCHECKを置く。
- 日付status=NULLではcomment=NULLかつ区間0件を保証する。statusがmaybe以外でも区間0件。コメント付きの日付が自動判定で未回答になる場合は削除確認が必要で、未確認ならイベント全体を無変更にする。
- 手動で変えた日付は、その日付の記号と△時間をまとめて保護する。コメントだけを編集しても判定の自動反映を止めない。詳細時間は枠単位で保護する。
- sourceはクライアントの申告を信用せず、サーバー側で手動入力と予定判定の経路から設定する。
- 新方式の保護は回答行へ集約し、旧方式用user_event_availability_overridesへ二重保存しない。新しい保護専用テーブルも増やさない。

### 過去案から省く構造と理由

- finalized_candidate_days: 確定が候補日ごとの集合である現要件では、候補日のconfirmed_atで表せる。履歴・承認者などの要件を先取りしない。
- 回答ごとのis_active: 対象日と日時候補の引退状態から有効性を導出できる。
- 候補版テーブル: 時刻が不変の候補IDとretired_atで保持・復帰を表せる。初回に変更履歴モデルを作らない。
- 汎用ワークフロー、イベント別timezone、段階ごとの提出日時: 現在の日本時間仕様・集計・明示保存のために必要なデータに限定する。
- △区間のJSON化: テーブル数の削減だけで採用しない。区間の型・参照・検証を明確にするため別テーブルとする。
- 旧availabilitiesの共用: 表現上はtrue/false/行なしを使えるが、旧RPC・MCP・同期の全経路を同時変更するリスクが高い。詳細時間回答を分離する。

## 状態と不変条件

Dを確定日集合、Pを確定前の明示時間対象日集合、Fを確定日時集合とする。

- 有効時間対象日は、Dが空でなければD、空ならP。
- 初回の日付確定でPを同じトランザクション内でクリアする。全日付の確定解除後もPを自動復活させない。
- Fに属する日時候補の親日付は必ずDに属する。確定・集計へ使う候補は引退しておらず、有効時間対象日内にある。
- 日付確定から除外しても候補・日付回答・詳細回答は削除しない。再追加で復帰するのは同一候補への回答で、解除したFは自動復活しない。
- 候補日追加では既存のD・P・Fを変更しない。新候補は未回答。
- adjustment_stageとD・Fは別概念。日付確定を維持したままtimesへ進める。
- 新方式の確定状況はD・Fから取得する。既存表示向けis_finalizedが必要ならDが空でないことの派生値として同一トランザクションで更新し、final_date_idへの旧フォールバックは新方式で使用しない。

### 時間候補の同一性

時刻・親日付を既存候補IDのまま変更しない。変更する場合は旧候補を引退させ、新候補を作る。確定済み候補の引退は確定日時の解除確認と一括処理し、参照切れを残さない。

当日0時〜翌6時を扱うため、隣接候補日から同じ実時間を指定できる。ここでは候補日を入力時に明示し、同じ時刻でも別の候補日に属する枠を別IDで扱う。自動的な所属日の付け替えや、別の日付への回答転用はしない。

このため、以前の「UNIQUE(event_id,start_time,end_time)を全方式で維持する」案を再検討し、次を設計上の第一候補とする。

- 旧方式: candidate_day_id IS NULLの行に対するUNIQUE(event_id,start_time,end_time)。既存行の重複禁止を維持。
- 新方式: candidate_day_id IS NOT NULLの行に対するUNIQUE(event_id,candidate_day_id,start_time,end_time)。
- 同じ候補日・同じ時刻の再追加は元IDを再利用し、引退済みなら復活させる。別候補日の同時刻へ回答を転用しない。
- 新方式では、同じ親日付内の有効な候補時間の重複を認めない。隣接する親日付間の重複は検討候補として許すが、確定時に実時間が重なる枠を同時確定しようとした場合は確認画面へ戻し、片方を選び直す。ICSや予定ブロックへ二重出力しない。
- 例: 11/7の翌2〜3時と11/8の当日2〜3時は別候補・別回答。片方を確定しても他方を確定した扱いにしない。11/7を確定から外した場合に解除されるのは11/7に属する確定枠。
- 制約の切替は、旧RPCやアプリが旧制約名・ON CONFLICTの対象に依存しないかを全件照合してから実装する。ローカルのマイグレーションとsrc/lib内ではevent_datesの同時刻キーをON CONFLICT対象とする記述は確認していないが、本番関数定義は未検証。DDLは未作成。
- 新しい索引を準備してから旧制約を切り替え、旧方式の重複拒否が途切れないようにする。所要ロックと既存行への影響は隔離DBで確認する。

開始＜終了、△だけが区間を持つこと、新旧モードと候補参照の整合、FとDの包含をDB制約・RPCで保証する。単独FKだけに依存しない。表をまたぐ不変条件のトリガー要否と更新順序はDBテストで確定する。

## Server Action・RPCの契約案

名前は役割を表す仮名。Web境界で公開トークンからイベントを解決し、内部RPCもイベント所属・方式・入力を再検証する。

| 操作                    | 入力・原子的な処理                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------- |
| createDateFirstEvent    | 基本情報・候補暦日・任意時間帯設定。イベントと候補日を一括作成                                                      |
| addCandidateDays        | 公開トークン・expectedEventRevision・追加暦日。重複を検証し、既存データを変更せず追加                               |
| saveDayAnswers          | 公開トークン・作成/編集の区別・participant ID・expectedDayRevision・日別差分。回答/コメント/区間を一括保存          |
| configureTimeAdjustment | 公開トークン・expectedEventRevision・対象日・候補時間。PまたはDの規則に従い候補を追加/引退し、段階を更新            |
| saveTimeAnswers         | 公開トークン・作成/編集の区別・participant ID・expectedDetailRevision・時間別差分。対象内で引退していない枠だけ保存 |
| setFinalization         | 公開トークン・expectedEventRevision・希望D/F・確認済み解除日時集合。最新差分を再計算し一括確定/解除                 |

- 日付・時間の差分にない対象は不変。日付status:nullは当日の回答値・コメント・区間を消し、手動未回答の保護行を残す。詳細availability:nullも値NULL・source=manualの行で保護する。
- 新規参加者と初回の対象段階の回答は同一トランザクション。日付段階を通らず詳細時間段階で初めて参加する場合も対象とする。既存ID不明を名前検索や新規作成へフォールバックさせない。
- 新規作成は同じ作成要求を再送してもイベント・参加者を増殖させない。creation_request_idと初回正規化入力のhashを作成先の行へ保存する。後述の再送契約に従い、汎用冪等性テーブルは作らない。
- 更新の二重送信は重複行を作らない。古いrevisionの再送は安全な競合応答でもよい。「同じ内容に見える」だけで他の編集後の再送を成功扱いしない。
- 重複ID、不正な日付、別イベントID、区間の逆転、過大な区間数・コメント長・一括入力を拒否する。隣接区間は結合可能だが空白を埋めない。
- 確定日から外す場合、関連Fが1件でもあれば最新日時を示した確認が必要。確認集合とrevisionが一致しなければ書き込まない。
- △の提案は保存済み詳細回答を上書きしない。未確認の初期案を正式な時間集計へ含めない。
- 成功は保存値と新revisionを返す。失敗は入力不正、対象不一致、競合、再確認、再試行可能を区別し、利用者が次に取れる操作を示す。内部詳細・トークン・参加者情報をログへ出さない。

### 同時更新と読み取り

1. 回答保存はイベント行をFOR SHAREでロックし、方式と構造revision・対象範囲を確認する。
2. 続いて参加者行をFOR UPDATEでロックし、日付用または詳細時間用revisionを比較する。
3. 差分を保存して該当revisionだけを進める。他参加者の保存や日付/時間の別段階の保存で不必要に失効させない。
4. 構造変更・確定変更はイベント行をFOR UPDATEでロックして、D・P・F・候補状態を再検証する。回答保存の共有ロックと競合させ、対象検証から保存の間の構造変更を防ぐ。
5. 回答保存中にlast_accessed_atなどをUPDATEしてイベント共有ロックを昇格させない。アクセス記録は既存のレスポンス後処理などへ分離する。
6. 全更新経路でイベント→参加者の順を守る。読み取りはD・F・revisionを同一スナップショットで返すDB境界を用意する。

日付・時間のrevisionが独立していても参加者行ロックは共有するため、同じ参加者の保存自体は短時間直列化する。初回から日別revisionを増やさず、実測で必要なら再検討する。

回答保存でイベント構造revisionの一致は必須にしない。IDの意味が不変で、全変更対象が現在も同じイベントの有効範囲内なら保存する。別の日付が追加されただけでは拒否しない。引退・対象外を1件でも含むパッチは全件無変更で返す。応答には現在のeventRevisionを含め、追加候補の再表示へ使う。

## 権限・互換性・連携

- 新テーブルにもRLSを有効化し、PUBLIC・anon・authenticatedの直接アクセスを認めない。新関数もPUBLICからの既定EXECUTEを含め明示的に制限する。service_roleはサーバー内だけで使う。
- 関数は必要以上にSECURITY DEFINERにしない。採用時は固定search_path、スキーマ修飾、実行権限を検証する。
- Webのサーバー境界で公開トークンと対象所属を確認する。ユーザーの主催者/参加者権限を追加することではない。
- Server ActionsのOrigin/CSRF対策、読み取り用Route Handler、入力件数・文字数・頻度制限を既存実装と照合する。エンドポイントを不必要に増やさない。
- 旧RPC、MCP、アカウント同期・コピー等から新方式を更新できないようtime_firstのガードを設ける。取得側もscheduling_modeで分岐する。画面の分岐だけでは不十分。
- 新方式の取得型は日付回答・三値の詳細回答・D/Fを返す。旧型へ変換して欠落をfalseで埋めない。汎用リポジトリ層は作らず、既存のサーバー取得境界に方式の判別を置く。
- 他参加者を編集したWeb操作を、編集者本人のアカウント予定・user_event_linksへ自動反映しない。個人機能は本人としての対象選択と明示操作を分ける。
- 初回からMCP既存8ツールとアカウント予定による日付/時間の補完・同期を新方式へ対応させる。旧boolean用の経路はtime_firstに限定したまま、新方式の三値・手動保護へ明示分岐する。
- 日付のみ確定は時間の競合を作らない。現在有効な確定日時だけをアカウント予定の競合参照へ反映する。DB確定と外部サービス同期を同一トランザクションにはせず、失敗と再試行を区別する。
- ICSは日付のみと日時付きの出力を区別する。日付ごと/候補ごとのUID、切替・解除、個別指定の所属確認をテストする。静的ファイルや追加リンクで取り込んだ外部予定の自動更新・削除は保証しない。

## 時間・提案・出力の具体契約

### B1: 当日から翌6時まで

候補日の0時を0分とし、区間は整数分による半開区間で0 <= start < end <= 1800とする。前日を表す負値と翌6時超過を拒否する。詳細時間候補も同じ範囲内に収める。入力グリッドは1時間単位を維持するが、予定補完で取得した端数区間は丸めず保持する。

| 例                                  | オフセット  | 判定                      |
| ----------------------------------- | ----------- | ------------------------- |
| 11/7 23時〜11/8 1時                 | [1380,1500) | 許可。11/7の23:00〜翌1:00 |
| 11/7 23時〜11/8 0時                 | [1380,1440) | 許可。終了は24:00         |
| 11/8 5時〜6時を11/7の候補として指定 | [1740,1800) | 許可。翌5:00〜翌6:00      |
| 翌6時〜7時                          | [1800,1860) | 拒否                      |
| 前日23時〜当日1時                   | [-60,60)    | 拒否                      |
| 12/31 23時〜1/1 2時                 | [1380,1560) | 年境界を含め許可          |

○の日付判定は[0,1440)で、[1440,1800)は含めない。実日時は壁時計の暦日と分数から生成し、端末TZによるDateの暗黙UTC変換を避ける。DBでtimestampを扱う既存方針を維持する。

### B2: 初期案

区間を整列し、重複・隣接だけを結合してから候補枠全体の被覆を判定する。18〜19時と19〜20時は18〜20時を覆うが、18〜19時と20〜21時は18〜21時を覆わない。

戻り値は保存済み回答とsuggestedAvailabilityを分ける。提案を採用して正式保存する際はmanual由来の回答とし、未確認の提案を回答人数へ含めない。アカウント由来の補完とは由来を混同しない。

### B3: 出力

確定日ごとにFがあればその枠を出し、FがなければDATEの予定を1件出す。日付のみUIDはevent ID＋day ID＋date種別、日時付きは既存のevent ID＋slot IDを使い、互換性のため旧方式のUIDを変更しない。現行のUIDドメイン表現をこの機能だけで変更しない。

日付のみICSはDTSTART;VALUE=DATE:20261107、DTEND;VALUE=DATE:20261108、TRANSP:TRANSPARENT、タイトル「イベント名（時間未定）」を基本とする。日時付き予定へ切り替えた後に古いDATE予定を自動削除できると説明しない。複数枠への変化を1つのUIDの更新として偽装しない。

Google追加リンクは日付のみと時刻付きで明示分岐する。Calendar APIのstart.date/end.dateと、現行のTEMPLATEリンクで利用できるパラメータは同一仕様ではない。リンクでのDATE表現・空き時間設定の可否は実画面で検証し、未検証の空き時間パラメータへ依存しない。

### B6: 日付未確定から日時を確定

UIは選択日時の親日付を希望Dへ加え、新規の日付確定と日時確定を同時に確認させる。RPCは送られたD/Fの包含だけを検証し、Dを勝手に補わない。候補日の異なる重複日時の同時確定も拒否する。

## B4: アカウント自動反映とMCP

### 日付と時間の判定

日付の基準は当日0〜24時。アカウントの可・不可区間と他イベントの確定日時を同じ壁時計で比較する。不可を優先して可区間から差し引き、残りの可・不可・不明の被覆を計算する。

- 全基準時間が可ならyes、全て不可ならno。
- 可区間があるが全面可でなければmaybe。△区間は既知の可区間を保持する。
- 可区間がなく不明が残れば未回答。部分的な不可だけから全日×と判断しない。
- 翌0〜6時の可否は日付記号の判定に混ぜない。判定がmaybeの場合だけ、翌朝の既知の可区間も△区間へ追加する。詳細時間への補完では翌朝の実際の予定も参照する。
- 詳細枠は不可との重複でfalse、不可がなく全面可ならtrue、それ以外はnull。nullをfalseで埋めない。
- 手動由来は保護し、account由来だけを再計算する。手動保護の解除は対象と差分を確認した操作に限定する。
- 未回答への変更で日付コメントが消える場合、確認前には当該イベントを全件無変更で返す。確認入力と現在の回答・予定を再照合する。
- 予定補完の端数は分単位で保持し、グリッドの部分セルや実区間の参照表示で表す。手動操作前に全1時間の可へ丸めない。
- 初期案を読み取るだけでは保存せず、回答送信・MCP保存・本人が選んだ予定反映で正式保存する。予定からの判定はサーバーで再計算する。

本人が行う予定反映は、未来の日付候補と、現在の時間対象日内かつ引退していない時間候補を対象にする。対象外の日付に属する詳細回答・引退候補・過去候補は、source=accountでも更新せず復帰時の記録を保つ。日付の記号・詳細時間の変更を同時に適用するときは、各段階のrevisionをともに検証する。

予定反映のプレビューには、対象回答revision、source、候補状態、読み取った予定・確定日時の指紋を含める。適用前に再計算し、変わっていれば無変更で再プレビューを求める。複数イベントの同期は既存と同様にイベント単位とし、成功・要確認・失敗を区別する。

### MCPのツール対応表

OAuthのdaysynth.read/writeを維持し、本人回答の参加者はuser_event_linksから解決する。get_eventの公開イベント情報はOAuth＋公開トークンで参照し、本人回答・個人予定の取得更新は本人紐付けを必要とする。未紐付けの初回回答は認証済みuser IDとイベントでロックし、新参加者とリンクを一括作成する。

| 既存ツール                 | 日付先行型での対応                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| list_my_events             | 候補日・確定日を時刻未定のまま検索。日時確定と混在しても欠落させず、mode・確定種別を返す                                 |
| get_event                  | 候補日、時間候補、D/F、現在の段階、eventRevisionを取得                                                                   |
| get_my_answer              | 本人の日付status・△区間・コメントと時間回答・各revisionを取得。include_account_scheduleで正式回答とは別に予定判定を返す  |
| get_my_schedule            | 既存どおり本人の予定を取得。時刻未定を擬似時間ブロックとして追加しない                                                   |
| save_my_answer             | 新方式はanswer_kind=days/timesで入力形を分け、nullableな差分と対応revisionを必須にする。日付・時間それぞれ本人だけを保存 |
| save_my_answer_to_schedule | 本人の正式な詳細回答の指定枠だけをpreview/apply。未回答と日付のみの回答は時間ブロックへ変換しない                        |
| preview_my_schedule_update | 変更予定で日付/時間の反映差分を計算。手動保護・コメント削除の要確認を表示                                                |
| update_my_schedule         | 予定保存後、本人に紐づく新旧イベントへ方式別に反映。過去・確定済みの既存保護方針を維持し、部分失敗を返す                 |

旧方式では既存の入力・出力を維持する。新方式へ旧availabilities配列だけを送った場合は型不一致として拒否し、未回答をfalseへ変換しない。MCPから任意のuser ID・participant ID・sourceを指定させない。コメントの省略は不変、nullは削除を意味し、日付の未回答戻しでは必ずコメントも削除する。

手動・アカウント・△由来提案の優先順位は、保存済みmanual > 明示再反映可能なaccount > 未保存の提案。MCPのuse_account_scheduleで未回答を不可へ置き換える旧方式の挙動を新方式へ引き継がない。source=manualのNULLも保護する。save_my_answerはanswer_kindで指定した段階だけを更新し、反対の段階の回答を同時に作らない。

日付回答全体をアカウントへ保存することは行わない。詳細回答の可/不可区間だけを正確な時間境界で保存し、矛盾する重複はプレビューで拒否する。既存の1時間分割処理を新方式の端数へ無条件に適用しない。

## 保存・再送契約の具体化

### 新規作成

- 新規フォームの作成操作ごとにランダムUUIDのcreation_request_idを1つ作り、同じ送信の再試行で再利用する。入力を変更して別操作として作成する場合だけ新しいIDにする。
- eventsとparticipantsにNULL可のcreation_request_idとcreation_payload_hashを追加する案を採用した。旧方式行はNULLで、新方式の新規作成では両方を保存する。ハッシュはサーバーで正規化した元の入力・イベント・操作種別・認証済み主体から計算する。日付ID集合と区間は正規順序で直列化し、自動補完の再計算結果・生成済みトークン・サーバー時刻はhashへ含めない。同じ入力の再送を、予定が変わっただけで別要求として扱わない。
- イベント作成は要求IDで一意、参加者作成はevent_idと要求IDで一意。競合時は初回入力hashを照合し、同じ要求なら作成済みIDを返し、別内容なら全件無変更のrequest_conflictを返す。
- 再送で後続の編集を巻き戻さない。返すのは作成済みID、replayed=true、現在のrevision。初回の回答パッチを再適用しない。
- 要求IDとhashは再送制御専用で、編集の本人認証には使わない。公開read modelやselect('*')のクライアント転送へ含めず、ログにも出さない。
- 保持期間は作成先の行の存続期間。行の削除後までの恒久的な重複排除は保証しない。古い画面の失敗で新しい要求IDを自動発行しない。作成・再送を無制限に許さず既存の頻度制限と照合する。

### 回答と氏名の更新

更新は参加者の対象段階revisionで検証する。イベント構造が変わっていても対象IDが有効なら受理する。1件でも不正・対象外ならパッチ全体を拒否し、別の枠を部分保存しない。

氏名は日付/時間の双方から変わり得るため、変更するときだけexpectedNameも送り、参加者ロック後に照合する。名前変更なしの保存は現在名を維持し、古いフォームの名前で上書きしない。新しいmetadata revision列は追加しない。詳細時間段階で初めて参加する保存も、新規参加者作成の再送契約に従う。

### 読み取りの整合とロック

D/Fとrevisionは1つのSQL文による読取用RPCで取得し、別々のREST取得を組み合わせた混在スナップショットにしない。名前・回答・source・各revisionも同じ保存前提のスナップショットで返す。書き込みの行ロックはイベント→本人リンク（個人操作のみ）→参加者の順に統一する。個人操作でユーザー単位のadvisory lockを使う場合は、どのイベント行よりも先に同じキーで取得する。共有Webの回答編集では個人の予定・リンクを自動更新しない。

アカウント予定の適用は、プレビューの指紋の再確認に加え、SERIALIZABLE境界とユーザー単位のadvisory lockを揃える。既存の個人予定更新・紐付け変更の全経路とのロック順を実装前に照合する。異なるトランザクションで指紋を比較してから後で保存するだけでは競合を防げない。予定保存とイベント反映が別トランザクションであること、各イベントの再試行が必要なことは明示する。

### B5と実装前検証に残す内容

プリセット・表示範囲・氏名/コメント長は機能仕様の初期案を使う。入力日数・総候補数・要求サイズ、nullable CHECK・跨表制約とRPC契約は後述の2026-11-03詳細化へ整理した。頻度・実行時間は運用初期案、索引切替の時間と負荷は隔離DBでの検証対象とする。

＋位置・折り返し・長文・部分セルは実装後の実画面で最終調整する。これは日跨ぎ・○の意味・初回連携範囲を再び未決に戻すものではない。

## 入力境界・DB制約・RPC契約（2026-11-03詳細化）

この節は実装の目標となる契約。マイグレーション案は隔離DBだけに適用済みで、検証結果と残る作業は後述する。[機能仕様の入力上限](../../specifications/date-first-scheduling.md#入力上限の設計値2026-11-03)を設計値として採用し、DB実測による調整は記録する。

### 既存制限と要求サイズ

- src/app/mcp/route.tsのreadLimitedBodyは131072 bytes（128KiB）。src/lib/mcp/schemas.tsの旧回答配列は1000枠、氏名100・コメント2000。いずれも現状のコード上の値。
- next.config.tsにはServer ActionsのbodySizeLimit指定がない。公式資料の既定値は1MBで、multipart等の外側も対象。新方式Webの正規化JSONは768KiBとし、実HTTP本文に余白を持たせる。外側が必ず収まるという保証はせず、実装時に最大入力で確認する。
- 検証順は、HTTP本文のサイズ制限→厳密な入力スキーマ→件数と文字数→正規化JSONのバイト数→DB内の所属・最新状態。ファイルや未知のフィールドを許さない。
- MCPの128KiBは外側を含むため、1000変更でも大きい文字列を含めると先に本文制限へ達する。WebとMCPの値を同一と偽らず、MCPで超過した場合は全件無変更で対象を絞るよう返す。
- 新方式の文字数はコードポイント数、DBはchar_length。Zodの既存.maxだけに依存してUTF-16単位との不一致を作らない。正規化後の値へDB制約を適用する。
- 候補日数90と有効時間枠3000は、90日×30時間×1時間枠=2700枠を収める設計。10分枠を90日全体に生成すると16200枠になるため許可せず、生成前に見積もりを返す。基本の1時間グリッドと、既存の詳細時間枠の粒度を混同しない。
- 例として、90日×2000個の4-byte文字はコメントだけで720000 bytes。枠ID・区間を含めた実サイズも検証する。全項目を同時に最大値にできることまでは約束しない。
- 900区間は[0,1800)の整数分区間の理論上限。入力区間数も900以下を正規化前に検証し、重複区間を大量に送ってから縮める処理を許さない。区間和・日付ごとの順序・配列のソートはサーバーで正規化する。

### 頻度と実行時間の運用初期案

新たな制限用DBテーブルは作らない。初回公開時に、デプロイ先の複数インスタンスで共有される入口制限を利用できることを確認する。

| 境界                     | 初期案                                             | 確認すること                                                                  |
| ------------------------ | -------------------------------------------------- | ----------------------------------------------------------------------------- |
| 新方式Webの更新          | 同一IPで120要求/分                                 | 共有回線の50人が各1回回答するケースを妨げない。プレビューと再送も負荷へ含める |
| 新規イベント作成         | 同一IPで10要求/10分                                | 通常更新とは別枠。同一要求の再送で新イベントを増やさない                      |
| MCP                      | 現行のgrant単位60要求/分を維持                     | 現行はプロセス内のカウンタであり、インスタンス間で共有される制限とは扱わない  |
| ロック待ち・文の実行時間 | まずlock_timeout 3秒、statement_timeout 10秒で検証 | 一般要求の初期案。実測せず本番の既存ロール全体へ設定しない                    |

IPだけをイベント内の本人識別に使わず、入力participant IDだけで頻度制限を回避できる設計にしない。制限時は再試行可能時刻または待ち時間を返し、入力を保持する。入口機能の有無は未確認であり、プロセス内制限だけで分散環境の対策が完了したとは報告しない。

### DB制約の責務

| 不変条件                                       | DBでの保証                                                 | 補足                                                                                 |
| ---------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| sourceはmanual/account                         | NOT NULLとCHECK                                            | NULLがCHECKを通過する性質に依存しない                                                |
| statusはyes/maybe/no/NULL                      | NULLを明示的に許すCHECK                                    | NULLはmanualの保護行だけ。status NULLならcomment NULL                                |
| availabilityはtrue/false/NULL                  | boolean型、NULLならsource=manualのCHECK                    | account由来の未回答は行なし                                                          |
| 区間の範囲                                     | 整数型と0 <= start < end <= 1800のCHECK                    | 日付境界の実日時変換とは分離                                                         |
| 参加者・候補の所属                             | UNIQUE(id,event_id)を参照する複合FK                        | 別イベントのUUID混入をRPCだけに任せない                                              |
| 区間の親                                       | day_response_idのFK、削除時CASCADE                         | status NULLの保護行に区間は保存しない                                                |
| 時刻の正方向                                   | 新方式に対する開始<終了の検証                              | 既存の不正行の有無を調べず旧方式へCHECKを追加しない                                  |
| 候補時刻の一意性                               | 方式別の部分一意索引                                       | 旧方式はevent/time、新方式はevent/day/time                                           |
| 作成要求の重複                                 | creation_request_idの一意索引                              | 参加者はevent_idとの組。同じID・異内容はhashで拒否                                   |
| 日付数・有効枠数・総枠数                       | イベントをロックした構造変更RPC内の件数検査                | 集合の件数を行単位CHECKの副問い合わせで表さない                                      |
| △以外の区間禁止                                | 親回答と区間の両方の変更を対象とする遅延制約トリガー       | status変更だけで不正区間が残る経路も検査                                             |
| Fの親日付はD内、有効候補、時刻重複なし         | 確定日・確定日時・候補引退変更を対象とする遅延制約トリガー | 新方式だけ検証。旧方式の既存確定ルールを変えない                                     |
| 方式と候補参照の整合・候補の時刻と親日付の範囲 | 候補作成/更新のガード                                      | date_firstは親候補日必須、time_firstはNULL。modeと候補の帰属・時刻の後書き換えを拒否 |

NULL制約の具体例は、status/availabilityがNULLならsource='manual'、日付statusがNULLならcomment IS NULL。sourceには別途NOT NULLを置く。status IN (...)だけでNULLも禁止したつもりにならない。旧方式用の既存テーブルへ新方式の氏名長などを一律CHECKとして加えず、既存行と互換性を確認した境界に限定する。CHECKで別テーブルを検索する関数を呼ばず、参照と跨表整合を分離する。

遅延トリガーはAFTER ROWのCONSTRAINT TRIGGERとして最終状態を検査する。イベントID・参加者IDの変更前後で必要な対象を検査し、古いNEW行だけを判定しない。親の削除でCASCADEされた場合は、親が消えたイベントの不存在を不正とみなさない。

公式RPCは全件検証後に書き込み、応答を組み立てる前に対象の遅延制約をIMMEDIATEへ切り替えて検査する。途中でFを外してDを変えるような正当な更新順序を許しつつ、最終状態が不正なら呼び出し全体を失敗させる。複数接続での保証には、これらのトリガーだけでなく前述のイベントロックも必要。

索引切替は、既存の旧一意制約を残した状態で旧方式用・新方式用の索引を作成し、確認後に旧制約を外す。新方式の二重帰属枠を作れるのは旧制約を外した後。新規作成入口を閉じて作業し、既存参照制約・依存関数・ロック時間を事前確認する。

### 共通の入力と結果

Web・MCPの外側は違っても、サーバー内部の正規化されたコマンドへ集約する。クライアントが渡したsource、user ID、mode、is_finalizedを更新根拠にしない。MCPのparticipant IDは本人リンクから解決する。

revisionはDBでbigint、JSONでは非負の10進文字列として返す。JSの浮動小数による比較へ落とさない。expectedEventRevision、expectedDayRevision、expectedDetailRevisionを別々に持ち、対象外のrevisionを要求しない。

| 結果コード                     | 更新           | 応答・再実行                                            |
| ------------------------------ | -------------- | ------------------------------------------------------- |
| success                        | 全件確定済み   | ID・現在のrevision・変更件数。新規再送ならreplayed=true |
| invalid_input / limit_exceeded | なし           | 項目と上限を案内。入力を切り捨てない                    |
| invalid_event_scope            | なし           | 他イベントの存在を詳述しないユーザー向け文言            |
| stale_revision                 | なし           | 最新の該当revisionと公開可能な現在値。自動上書きしない  |
| requires_confirmation          | なし           | 現在の解除日時・削除コメント対象・確認用の指紋          |
| request_conflict               | なし           | 作成要求IDの別内容再利用。別の作成操作を明示する        |
| retryable_error / rate_limited | なし           | 再試行可否と待ち時間。新規作成の要求IDを変えない        |
| success_with_warning           | 本体は確定済み | 予定反映・キャッシュ更新など未完了の後処理を区別        |

外側のHTTPエラー（本文過大など）とRPCの結果コードを混ぜない。SQLの権限・制約名・内部例外をそのまま利用者へ返さない。想定した競合は書き込み前に返し、予期しないSQLエラーは呼び出し全体をロールバックしてから変換する。途中更新後に通常の失敗値を返して部分更新を確定させない。

### 操作ごとの入力契約

日別パッチはcandidateDayIdと、任意のstatus・comment・intervalsで構成する。候補IDだけのパッチは拒否する。comment省略は現在値を維持、null/空文字は削除、status:nullはコメント省略でも削除する。コメント単独編集はstatusとintervalsを送らず、sourceを維持する。現在値が未回答なら非空コメントを拒否し、回答記号を入力するよう案内する。未回答に対するコメント削除だけなら無変更として扱える。statusまたはintervalsを明示した手動操作はsource=manualにする。

status省略ならロック内の現在値を使う。intervalsは最終status=maybeのときだけ0件以上の配列を受け取り、その他は省略または空配列。既存△の区間を保持したい場合はintervalsを省略し、△時間を明示的に空にする場合は空配列にする。新規△で省略なら0件。○/×/未回答へ変えた場合は区間を必ず消す。intervalsだけのパッチで非△を暗黙に△へ変えない。

時間パッチはeventDateIdとavailability:true/false/null。両パッチとも同じIDを2度指定したら拒否する。新方式の日時候補設定はcandidateDayIdとstartOffsetMinutes/endOffsetMinutesを受け、端末由来のUTC変換や曖昧な25時文字列を入力契約にしない。

新規回答の空パッチは全未回答の明示保存として参加者を作成できる。作成時は該当段階revisionを、実回答があれば1、全未回答の空パッチなら0とする。createで後から既存回答を更新しない。MCPの初回は本人リンクの既存有無を同じトランザクションで再確認し、既存参加者へ名前で合流しない。

編集では必要なexpected revisionを必ず比較し、その後に実変更の有無を調べる。同じ値の再送でも古いrevisionを成功に読み替えない。sourceがaccountからmanualに変わる操作、行なしから手動NULLになる操作は、可否の表示が同じでも実変更。

### 確認・予定反映の契約

確認はbooleanのconfirmed=trueだけでは受け付けない。解除対象のソート済みID集合、event revision、関連回答revisionと、必要な場合は予定スナップショットを正規化し、サーバーでSHA-256の指紋を作る。適用時に同じ入力から再計算し、合わなければ全件無変更で再確認へ返す。指紋は本人認証の証明ではなく、確認した内容が変わっていないことの照合に使う。

確定変更では、解除対象Fがあるときだけ確認を要求する。新規D/Fを確認画面で示すことと、解除のDB確認条件を分ける。日時候補の引退で確定Fが外れる場合もconfigureTimeAdjustmentの一括処理で同じ確認を行う。

自動反映で日付が未回答となりコメントを削除する場合は、対象candidateDayIdとcommentの現在値を確認指紋へ含める。コメント本文を外部ログへ出さず、無関係な参加者のコメントを確認情報へ載せない。

予定反映は、OAuth/sessionから解決した本人リンクの再確認、回答sourceとrevision、候補の有効性、予定と確定日時の再取得、指紋比較、差分保存を同じトランザクションで行う。SERIALIZABLEの再試行はトランザクション全体を最大2回までとし、各回でリンク・確認内容を再検証する。失敗が続けばretryable_errorを返す。409相当のstale_revisionやrequires_confirmationを自動再試行して確認を飛ばさない。

複数イベントの同期は1イベントずつコミットする。結果にupdated / unchanged / requires_confirmation / failedを返し、失敗イベントだけを再プレビュー可能にする。既に保存した本人の予定を再度新規作成しない。

#### 実測と移植時の修正

試作では、行ごとの遅延トリガーがイベント全体を繰り返し検査していたため、回答に関する検査を変更対象へ絞り、確定のないイベントの走査を省略した。マイグレーション案にも反映した。50接続の保存が成立することは確認したが、測定値はローカルの単発値であり、本番負荷の保証値にはしない。

マイグレーション案へ移す段階では、次も修正した。

- 隔離DBの初期化はsearch_path=publicを明示する。過去のロール既定値を引き継ぎ、既存履歴表を別スキーマへ作ってしまう再実行時の問題を防ぐ。CLI生成型に既存履歴表・RPCが含まれることも確認する。
- ハッシュはPostgreSQL組み込みのsha256を使い、pgcryptoの配置スキーマに依存しない。公開トークンはランダムUUIDから生成する。
- 本人リンク付き初回保存の再送照合はIS DISTINCT FROMを使い、NULLを比較した結果で別要求を通さない。
- 確定日時の複合FKは元の単列FKを置き換え、参照名とON DELETE CASCADEを維持する。参照を2本にすると既存PostgRESTの埋め込みが曖昧になるため。隔離PostgREST v14.13から従来のevent_dates(start_time,end_time)取得が成功することも確認した。
- 旧方式の日時編集へ新方式の不変制約を広げない。参加者削除時は新回答と区間をCASCADEで削除する。
- 予定・本人リンクの更新トリガーで本人ロックを取得し、既存の書き込み経路も同じ規則へ揃える。直列化失敗・デッドロックは専用サーバー境界で最大2回再試行し、古いrevisionや確認指紋は再試行で上書きしない。
- 公開用の既存取得関数でも、creation_request_id/creation_payload_hashはNULLへ伏せる。新しい取得モデルは公開項目だけを組み立てる。

#### アプリ連携の到達点と残る作業

[入力スキーマ](../../src/lib/date-first-schema.ts)、[専用サービス](../../src/lib/date-first-service.ts)、[Server Actions](../../src/lib/date-first-actions.ts)を経由して、作成・日付回答・集計・候補設定・詳細時間回答・日付/日時確定と解除の画面を接続した。匿名の新規回答と明示選択した既存回答の共同編集を維持する。入力準備前のハイドレーション中はフォームを無効にし、入力やチェック変更を取りこぼさない。

日付先行型のWeb・MCPで保存トランザクションの開始・タイムアウト・再試行・接続解放を共通化した。ロールバックが失敗した接続は再利用せず破棄する。予定反映の実値比較も画面とサーバーで共用し、IDの索引で照合する。公開契約とDB構造は変えていない。規約チェック欄はコンポーネントごとにIDを生成し、画面切替中に複数フォームがDOMへ残ってもラベルの操作先が重ならないようにした。

既存8つのMCPツールは方式別の契約を持つ。本人回答の取得・初回予定補完・差分更新、候補/確定内容の取得、本人イベント検索、予定変更の事前確認と反映、正式時間回答の予定保存を実装した。MCPの実DB・SDK統合2件と期間検索のSQL統合11件が成功した。SDK統合は[専用実行スクリプト](../../scripts/test-date-first-mcp.mjs)から一時PostgRESTを起動してCIでも再実行する。実HTTPではOAuth認可・権限・失効と8ツールの列挙を確認した。WebはJSONとmultipartの外側を含む要求を送り、正規化済み入力767/768KiBがDB照合へ進み、769KiBがDB接続前に拒否されることを確認した。MCPは本文127/128KiBを受理し、129KiBを413で拒否することをContent-Length有無の両方で確認した。

Webでは本人の回答を明示的に紐付け、予定との差分を確認して反映する。アカウント画面は新方式の差分対象へのリンクを示す。コメント削除を伴う自動未回答化は、対象イベント全体を確認後に反映する。Webの予定更新後は差分確認へ進み、MCPの予定更新では確認済みの対象へ反映する。正式時間回答から予定への保存は別の明示操作で、他イベントの回答を更新しない。旧boolean同期経路は新方式を除外する。

カレンダー出力は、日付だけの確定を日付型・TRANSPARENTのICSへ、時間確定を日本時間の日時へ変換する。Google追加リンクも同じ確定内容から生成する。日付確定と時間確定のUIDは区別し、時間だけの解除後に日付UIDを維持する。ICS本文・Googleリダイレクトのパラメータは検証済みで、Google/Appleカレンダーへの実際の取り込み操作は未実施。

新方式の匿名E2Eでは作成から翌朝までの△回答、同名の新規回答、時間提案の明示採用、日付/日時確定・解除・カレンダー出力までを確認した。本人連携E2Eでは明示リンク、コメントだけの編集によるsource維持、コメント削除の取消/承認、30分の正式回答の予定保存を確認した。320pxの実ブラウザでタッチドラッグ中の行高固定、終了後の△展開、キャンセル時の復元を確認した。時間セルの最小幅は24.375pxで横はみ出しなし。モバイル/デスクトップ、ライト/ダークの画像はGit管理外へ保存し目視確認した。7・20・50人の結果、長い氏名と複数区間を320pxで確認し、日付と人数が重ならないよう日付を年の区切りで折り返した。reduced-motion設定での表示、キーボードの記号解除、破棄確認のEscape、結果から回答へ進んだ後のブラウザ「戻る」でbeforeunload警告が出て入力を保持することも確認した。

公開前に残る作業は次のとおり。

- 分散環境の公開頻度制限を共有入口に設定し、実際に検証する。プロセス内制限や新規DBカウンター表で代用しない。
- 本番既存行の整合、関数依存、索引切替のロック時間を確認する。本番適用・デプロイ・外部カレンダーへの書き込みは未実施。

最新版のlint・typecheck・buildが成功し、Jestは576件成功・DB環境変数未指定による統合14件スキップ。Chromiumは公開24件・認証8件、別実行のWeb本文境界1件・MCP HTTP/OAuth 2件が成功。専用DBの統合テスト結果は前述のとおり、別途確認した。

新規作成と作成画面の方式切替はENABLE_DATE_FIRST_SCHEDULING=trueの場合だけ有効で、既定は無効。既存の日時先行型を既定の入口として維持する。上の公開条件を満たすまで本番では有効化しない。

## マイグレーション・デプロイ計画

ユーザーの実装着手許可により、20261103060811_date_first_scheduling.sqlをCLIで作成した。適用先は隔離DBだけで、本番・通常開発用Supabaseには適用していない。マージ前に本番適用が必要であることと、以下の順序を明示する。

1. 隔離DBで既存マイグレーションを適用し、追加列・テーブル・FK・方式別一意索引・RPC・権限を検証する。
2. 本番への追加DDLと旧経路の方式ガードを、旧アプリのtime_first操作を維持できる順で適用する。複合FK・索引の既存行への影響とロック時間を確認する。
3. 型と方式分岐が追加列を参照するため、DBマイグレーションを先に適用し、その後で両方式に対応したアプリをデプロイする。新方式の作成入口は確認完了まで公開しない。
4. 旧方式、個人予定、MCP、カレンダーと新方式の主要フローを確認し、新方式の作成を公開する。
5. 作成公開後は日付先行データが存在するため、方式未対応の旧アプリへの単純ロールバックを行わない。必要なら新規作成を停止し、既存の新方式データを扱える版を維持する。

実装時のPR本文と完了報告には、実際のマイグレーションファイル名、本番で必要な作業、アプリとの適用順、適用後確認、復旧方針を記載する。権限修正済みの本番へ古いREVOKE計画を重ねたり、データを消して戻したりしない。基盤追加は未公開としてCHANGELOGへ記録し、機能の公開時に利用者向けの変更を追記する。

## 検証計画

- DB: 別イベントのID混在、重複回答、△以外への区間、falseと手動NULL/行なし、sourceの整合、全未回答、差分保存、確定集合の包含、候補引退と復帰、旧RPC拒否。
- 並行処理: 同じ参加者の古いrevision、名前だけの競合、候補追加後の有効パッチ、回答保存と確定解除、予定の同時更新、コメント削除確認の変化、同一作成要求の再送と異内容衝突、途中例外での全件ロールバック。複数接続で競合を再現する。
- 権限: anon/authenticatedからのテーブル直接操作・RPC実行を拒否し、サーバーからの公開URL操作は維持。既定権限も検証する。
- Unit: actions、calendar、MCP、予定同期、回答・集計・確定画面の関連テストを追加・回帰確認する。○の全日被覆・部分可・全面不可・不明、翌朝を○判定へ混ぜないこと、NULLの手動保護、隣接候補日の同時刻別ID、重複日時の確定拒否を含める。
- 全体: npm run lint、npm run typecheck、npm run test:ci、npm run build、npm run test:db:data-api、npm run test:e2e:chrome。
- UI: 機能仕様の幅・テーマ・人数条件でPlaywright実画面確認とスクリーンショットの目視確認。ドラッグ開始/終了/キャンセル、スクロール、フォーカス、reduced-motionを含む。画像はGit管理外へ保存。
- 文書のみの変更: git diff --checkと対象MarkdownのPrettier確認。実装・DB・実画面を確認していない段階を確認済みと記録しない。
